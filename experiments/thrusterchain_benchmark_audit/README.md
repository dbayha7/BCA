# ThrusterChain benchmark audit — 2026-10-26

## Verdict and scope

ThrusterChain is a useful controlled diagnostic, but the material inspected here does not yet establish a robust, general offline RL benchmark. The older `experiments/shift` study is a specialized TD3+BC/BCA mechanism experiment. The separately packaged `experiments/thrusterchain_bca/titan_20261026/payload/transfer_bundle/core_v4` supplies a time-aware finite-horizon environment, episode datasets, a BC baseline, and an adapter protocol. It explicitly describes its results as an integration smoke profile and lists research-scale multi-algorithm comparisons as future work. The two versions have different observation and termination contracts and should not be mixed silently.

This audit is based on repository source at commit `448cce46c922862cd9177f28e982ac0898bb38ca`, plus the existing untracked checkout state. It is not a certification of all learners, all datasets, or earlier results. No full training, sweep, tuning, or new scientific comparison was run. Hashed and historical source, datasets, and receipts were not changed.

## Findings, in priority order

1. **The v4 adapter contract cannot directly supply ReBRAC's dataset next action.** `core_v4/thrusterchain/training_runner.py:64` assembles episode-local successors correctly, but its `TransitionBatch` in `training_protocol.py:183` does not carry `next_actions` or `next_action_valid`. `core_v4/run_benchmark.py:42` separately exports both, with last steps invalid. An adapter consuming only the runner batch cannot reconstruct the correct next action after random minibatch sampling. A versioned interface should construct next actions within episodes before flattening, propagate the validity mask through selection and replay, and test the actual ReBRAC terms that consume it. Online partial episodes and truncations need explicitly defined handling. Do not substitute policy actions without identifying a changed objective.

**V4 continuing-mode caveat:** The optional continuing-time-limit dataset path forces a time-aware observation (`datasets.py:485-486`) and bootstraps at truncation (`training_runner.py:69-76`). Its final successor has remaining time 0, while all current observations in the collected episodes have remaining time at least 0.01. The time coordinate's continuation is not defined by the 100-step wrapper, and a subsequent decrement would fall outside its declared observation space. A valid post-step physical observation alone does not resolve this state representation. Define a coherent continuing-state representation and its target before using this mode for a benchmark; this issue does not apply to the default finite task's zero-bootstrap end.

2. **The legacy filtered export is unsafe for loaders that reconstruct successors by adjacency.** `experiments/shift/dataset.py:233,267` exports six arrays after removal without episode/step identity. If a removed step lies between retained rows, the explicit `next_observations[i]` remains correct but `observations[i+1]` is a different state. The internal legacy learner reads the explicit field (`learners.py:243`) and is not shown to have this defect. The source text at `dataset.py:33-37` should not be read as a guarantee for every standard loader. No actual corrupted run was identified. The read-only `data_tools_v1` checker demonstrates and detects mismatches, but matching observations cannot prove next-action provenance.

3. **Algorithm and experiment validation is incomplete.** V4's runnable default is offline-selected BC; its affine SGD adapter is a protocol example, not a neural offline RL baseline. Native TD3+BC synthetic checks in the handoff are not an end-to-end ThrusterChain algorithm comparison. The reviewed evidence does not establish task-specific TD3+BC, IQL, CQL, ReBRAC and Unifloral update/target correctness and matched experimental budgets. Integrate each named host as a separately identified version, trace actual losses and update schedules, and test a real task batch and checkpoint round trip. Declare dataset, preprocessing, reward, action coordinates, target masks, update counts, selection budget, and final evaluation for each.

4. **The shift claims need precise scope.** The plant is a deterministic synthetic coupled-oscillator control task; the shifted families change initial conditions, not the transition law. Current and wave ranges extend beyond the recorded ranges, while big kicks change Gaussian scale and overlap the recorded distribution. The v4 action-box mixture can construct rare or absent requested-action regions; that does not supply a known trajectory occupancy ratio. Claims about stochastic dynamics, changed actuator dynamics, real robotics, long-horizon stitching, or general offline RL robustness require additional tasks and evidence.

5. **Final evaluation must be isolated and uncertainty must match the replication unit.** The legacy fixed banks have been repeatedly used in development and acceptance, and should be treated as exposed. Its per-bank episode standard errors describe variability conditional on each fixed trained policy, not variability over independently trained seeds. Freeze configurations and selection procedures before final reporting, retain paired starts where appropriate, report individual returns and independent training seeds, and account for any online selection interactions separately. A seed namespace or a label called `final` does not by itself make a holdout uninspected. The additive `../thrusterchain_benchmark/evaluation.py` supplies separate reproducible streams, stable episode prefixes, bank identities, and actual legacy Gymnasium rollouts; it is not wired into or a validation of v4.

6. **Do not conflate legacy truth calculations with deployed evaluation.** `experiments/shift/truth.py:67-108` rolls the float64 dynamics and can use a float64 policy copy; `experiments/shift/thruster_chain.py:438` casts commands to float32 at the Gym boundary. Thus those calculations are values for their stated numerical rollout, not automatically bitwise-identical deployed Gym returns or gradients. V4's regular frozen evaluation steps its wrapper and is not shown to have this issue. The legacy bank generator also changes earlier starts when its requested size changes; v4's built-in evaluation uses episode seeds instead.

7. **The full v4 test suite is not reproducible from this checkout alone.** On Windows with the project `.venv` and cached Gymnasium path, `python -B -m unittest discover -s tests -v` ran 167 tests and ended with 25 errors; missing historical `results/smoke_v2` and `results/revision_v2_smoke` artifacts caused the observed errors. The handoff README says separate runtime assets are required. Restore only verified matching assets before claiming a full-suite pass; do not fabricate replacements for historical receipts. This result does not establish that the remaining errors or the complete suite pass after restoration.

## Verified checks

- Legacy environment: 21 tests passed in WSL, including the JAX dynamics parity test. The Windows JAX test was blocked by Windows Application Control; the other 20 passed.
- The additive adjacency checker has four passing tests, including a filtered-step counterexample and a read-only HDF5 CLI check. It has not been run against an actual gapped export in this checkout.
- The additive legacy evaluation helper has two passing tests covering seeded bank identities, stable prefixes, environment action/observation boundaries, and paired comparison checks.
- Static inspection found that v4 uses full episode arrays, train-only splitting and finite-horizon termination with a time feature; its explicitly labeled continuing-time-limit mode uses distinct bootstrap semantics. Those checks do not prove correctness of an external learner.

## Work needed before a benchmark claim

Create a separately versioned benchmark release and preserve all existing hashes. Extend and test the host transition contract; validate each supported learner numerically and with a bounded end-to-end run; verify frozen checkpoint and normalization behavior; restore or independently regenerate appropriately labeled test fixtures; define a preregistered set of datasets, seeds, scenarios, budgets and reporting metrics; and run independent-seed comparisons on a final unexposed evaluation set. Add scenarios for the other intended failure modes only after specifying what each varies and what evidence would demonstrate the distinction. A successful plumbing test is not a scientific performance result.
