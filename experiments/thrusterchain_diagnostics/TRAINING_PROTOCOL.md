# Continuous ThrusterChain core training protocol

This protocol records the full core comparison authorized on 20 October 2026. It supersedes the suite's earlier statement that no learner training is authorized. It does not reinterpret historical continuing-task results or authorize changes to legacy experiments. Exact seeds, behavior parameters, source identities, resource limits, and output paths must be frozen in the run's resolved configuration before training. Outcomes must not be used to revise this configuration.

## Scope and budget

The core has 30 jobs: five independent dataset/optimization replicates, three critical-region retention levels (full, rare, zero), and two methods (native TD3+BC and native TD3+BC with BCA). Each policy observes both actuator regimes and both load levels in one training distribution. Evaluation reports all four regime/load strata separately as well as the equally weighted pooled result. The replication unit for comparisons is the independent trained replicate; evaluation starts are not additional trained replicates.

Every successful job performs 100,000 accepted critic/host updates with batch size 256 and policy delay two, giving 50,000 actor/target updates and 25,600,000 sampled training rows. This follows `experiments/shift/learners.py::LearnSettings`, which uses this budget for the actual ThrusterChain host. The repository's general D4RL configuration uses 1,000,000 updates and is a different experimental convention. Record attempts and accepted updates separately. BCA incurs additional calibration work; matched host update counts do not mean matched computation.

Use the repository's two 256-unit hidden-layer actor and twin critics, Adam learning rate 0.0003, tau 0.005, alpha 2.5, target noise 0.2, noise clip 0.5, and policy delay two. BCA uses the actual repository scale fit, Bayesian/conformal threshold, and dose implementation with its declared settings; record those settings and hashes. Warmup is 10,000 updates and refreshes occur after updates 10,000, 15,000, ..., 95,000 (18 refreshes). Primary reporting uses the terminal 100,000-update checkpoint. The 50,000-update checkpoint is descriptive, not a candidate for return-based selection.

This core does not include other host algorithms, extra context-frequency shifts, or intervention-placement ablations. Those are separate extensions. Full core completion is not completion of all possible method comparisons.

## Objective and method identity

Train and evaluate the new suite's objective: raw reward, horizon 100, discount one, no terminal reward, and zero terminal bootstrap. Observations have 15 coordinates: the 13 physical coordinates, observed episode-fixed regime, and remaining-time fraction. `done = 1 - bootstrap_mask` must terminate the Bellman target at the horizon even though the environment marks horizon exhaustion as truncation. Historical gamma 0.98/0.99, continuing-task bootstrap, and dataset reward transforms must not enter this adapter silently.

The deployed neural actor outputs bounded continuous commands. Float32 network observations/actions and float64 plant execution must be declared and identical between methods. Exact finite-companion dynamic programming remains a separate model. Its optimal values, occupancy tables, and support certificates do not certify the continuous actor.

## Offline data and pairing

Generate a frozen source log under a bounded randomized behavior centered on the finite-horizon LQR controller. Multiply the unconstrained LQR command by 0.6, clip each coordinate to the stall knee, and choose its nearest atom in `{-1, -KNEE, 0, KNEE, 1}`. For each coordinate independently, sample that nearest atom with probability 0.8 and a uniform atom with probability 0.2. Thus each atom has mass 0.04 plus 0.8 when it is the center, and the joint action mass is the product of its four coordinate masses. The center is never an above-knee atom, so the conditional probability of any above-knee command is `1 - 0.92**4 = 0.28360704`. Freeze these parameters before fitting; do not use evaluation returns to choose the behavior. Categorical masses are not smooth continuous action densities.

The critical region is fixed before outcomes: current at least 0.8 and any absolute command above the stall knee. Full/rare/zero retention changes only the pre-outcome inclusion probability of critical rows. Use the same complete source log and same retention random stream across retention conditions so retained subsets are nested. Preserve each transition's original next observation and terminal mask. Do not bridge missing rows or top up removed rows.

Generate 1,024 source episodes per replicate, each with horizon 100, with exactly 256 episodes from each regime/load context in a seeded random order. Physical starts and behavior random draws are independent across episodes conditional on this balanced context allocation; the context sequence is not an i.i.d. mixture draw. Before retention, use a fixed seeded permutation to reserve 128 entire episode IDs, leaving 896 training episodes. Share that reservation across all retention conditions and methods, and exclude every reserved episode row from optimization. Both methods within a retention condition use identical retained training rows, observation normalization, initial actor/critic parameters, and minibatch/target-noise streams. The BCA-only random stream must not alter the paired host stream. Normalization uses only the declared retained training complement. Record whether normalization is separately fitted by retention or shared from one predeclared training-only complement.

Different retention levels may have different row counts. This is intentional and must be reported along with draw counts and reuse rates. Neither method receives the removed transitions or evaluator-only complete log as training data. Calibration has the same retention rule as its corresponding training condition. Select one uniformly sampled retained row from each reserved episode by a fixed seeded rule, without outcomes; the bank has at most 128 rows and one source episode per row. An episode with no retained rows contributes no bank row, with no replacement episode or additional data generation. Do not replenish missing critical rows. Record retained counts, selected bank counts, unique source episodes, and critical/noncritical counts in each regime/load stratum.

Full retention means no deliberate deletion from the generated log; it does not imply full visitation or continuous action support. A continuous deterministic neural policy generally proposes commands outside a categorical behavior's atoms. Ordinary action-density ratios cannot repair that mismatch. Report critical-region retention separately from continuous action support.

## Calibration validity and refusal

The repository's `calibration.reference.certifiable` checks whether a bank can numerically produce a finite uniform-weight posterior threshold. At miscoverage 0.1, credibility 0.95, and 1,000 posterior draws its documented minimum is 36 scores. This numerical condition alone does not prove that a threshold generalizes to every context. Report unique episode counts and context coverage alongside score counts. Selecting one row per separately simulated episode avoids counting within-trajectory rows as independent calibration units; it does not remove the dependence imposed by balanced context allocation. The bank is reused for 18 adaptive refreshes, so this design does not claim the guarantee of a fresh, untouched holdout at each refresh.

Preserve native BCA behavior: no ready reference before the first refresh; retain the previous valid reference after an invalid refresh; preserve the implementation's response to a valid but uncertified/infinite threshold. Record ready, certified, threshold, scale validity, dose, support/refusal indicators, and any refresh failures. Empty or numerically insufficient banks must produce an explicit status rather than a fabricated certificate. Missing critical calibration examples preclude a critical-region calibration claim even if the pooled bank passes the numerical size check.

The native infinite-threshold fallback uses a unit behavior-cloning multiplier, not maximal caution. Its `bc_support_fraction` measures native dose usability: it can be one before the posterior is ready and zero with a ready infinite threshold. It must not be relabeled certified support or population action support. The host and a unit-dose BCA arm may also differ by floating-point reduction order; matching initialization and random streams does not promise bitwise-identical warmup trajectories.

An invalid native update must not count as an accepted training step. Stop and record the affected job if the implementation cannot make valid progress. A failed or refused BCA job does not prevent matched baseline jobs or fixed-controller evaluation from completing. Do not silently drop failed seeds from aggregate reporting. If an adapter adds any fallback beyond the native dose behavior, predeclare it and report its executed return as a distinct policy. Calibration uncertainty bands concern their explicit residual target; residual coverage alone does not establish long-horizon Q coverage.

## Validation, final test, and controls

Use disjoint source-generation, calibration-reservation/row-selection, validation, and final-test random namespaces. Training and calibration have disjoint episode IDs from the frozen source log. Freeze 20 independent start draws per regime/load context for descriptive validation at 50,000 updates and 100 per context for final testing at 100,000 updates. Pair methods and fixed controls on the same starts within each evaluation split. Draw physical starts from the declared initial law, with the context fixed for each stratum. Evaluation transitions never enter the replay buffer, calibration bank, or normalization statistics.

The evaluation seed values are 72001 for validation, 82001 for final evaluation, and 92001 for independent critic queries, under namespace 2026102002. Source generation uses namespace 2026102001. The failure diagnostic is any absolute position coordinate `state[0:10:2]` exceeding 3 in the pre-step or post-step state; this is a measured event, not an early terminal condition. Every finite rollout continues to its declared horizon.

There is no online selection budget in this core: no hyperparameter choice, early stopping, checkpoint choice, restart, or additional data collection based on validation or test returns. Validation may expose implementation errors; repairs require a new source/configuration identity and a recorded distinction from results produced by the old implementation. The terminal checkpoint is the primary result regardless of its return.

Evaluate the fixed-knee capped controller and regime-aware capped controller on the same starts even when a learned method fails. They provide a no-fit reference for indiscriminate caution versus use of the monotone regime. Keep any finite-model oracle and continuous fixed-start QP diagnostics explicitly separate from learned-policy population claims. An empirical average over the finite evaluation bank is a sample estimate, not an analytic population expectation.

Save per-start raw undiscounted return, regime/load, actual action bounds, above-knee frequency, critical visits, and completion/finite-value status. Report each replicate and the paired BCA-minus-baseline return difference by retention and context. Include mean and dispersion across the five independent replicates; do not treat 400 rollouts from one trained actor as 400 independent trained-method results. Any uncertainty interval must state its estimator and replication unit. Five replicates by themselves establish neither a tight interval nor a performance benefit.

The critic query bank uses four physical start draws per context, each crossed with times 0, 50, and 99. At every query compare six candidate commands: zero, all-negative knee, all-positive knee, all-negative one, all-positive one, and the deployed actor command. Evaluate each candidate by forcing its first action and simulating the deployed actor thereafter to horizon 100. Compare both critics and their minimum to that finite-horizon policy Q. Report action-ranking regret and a separately computed one-step Bellman residual. This designed query distribution is not the policy's occupancy distribution. These are point diagnostics; no long-horizon interval coverage guarantee is implied.

## Execution record and completion

Before launch, save immutable resolved configuration, exact source hashes, dataset/bank hashes, start-bank hashes, platform/library versions, and the complete job matrix. Use bounded resources that do not oversubscribe existing user jobs. Record wall time and actual compute separately for host and BCA jobs, and write append-only progress and failure status. Never overwrite an existing run directory.

A run is complete only when every planned job has a terminal success, failure, or explicit refusal record; successful jobs have verified update counts and loadable checkpoints; and all planned evaluation/control records are present. A launch, process ID, or first progress event establishes that training started, not that the experiment completed. Preserve partial artifacts and report precise blockers if execution stops.
